# ADR 0007: Browser companion trust boundary

Status: Proposed
Date: 2026-10-02

## Context

Phase 1 keeps browsers fail-closed: `normalizeObservation` drops any observation
whose resource is a URL, and `docs/roadmap.md` says browser metadata stays
unavailable "until a companion can enforce private/incognito boundaries". The
Accessibility path cannot make that promise — it only ever sees the frontmost
window, and it cannot tell a normal window from a private one.

The Host API cannot be reused as the intake: its routes sit behind the DSH
webserver's session auth (the plan-validation curls needed the SPA cookie), and
a browser extension cannot hold that cookie. A companion therefore needs its own
authenticated intake that the plugin itself controls.

## Decision

1. **Intake.** The plugin opens its own HTTP listener bound to `127.0.0.1` on a
   configurable port (default `19388`), separate from the DSH webserver. It
   accepts only `POST /companion/observation`, only with a valid pairing token,
   with a body-size cap and a rate limit. Nothing is exposed beyond loopback.
2. **Pairing.** The token is 256 bits of randomness generated by the host, stored
   in the history database (not in a file the extension can read), shown once in
   the client panel, and revocable ("rotate token" invalidates the old one). The
   extension stores it in `chrome.storage.local` and sends it as a header.
   There is no ambient authority: without the token the intake answers 401 and
   records nothing.
3. **Incognito is never reported.** The extension does not request incognito
   access and refuses to report a tab whose `incognito` flag is true, checked
   before any other work. A test pins both halves: the manifest does not opt in,
   and a mocked incognito tab produces no message.
4. **Site-level control.** The companion reports `origin + path` and the tab
   title; the Host applies the existing policy to it (the same `resource` rules
   the AX path uses), with a companion-specific default-deny list for
   credential-bearing origins is *not* needed because the token and the policy
   already gate it — instead the panel gains per-origin allow/deny shortcuts.
5. **URL normalisation.** The companion sends the browser's canonical
   `URL.origin + URL.pathname`; query strings, fragments and URL credentials
   are not part of that shape. The Host validates that shape independently
   before delivery and refuses userinfo or non-canonical origin/path metadata,
   so a buggy or modified paired companion cannot smuggle credentials, queries
   or fragments into a stored URL. `displayLabel` is the tab title.
6. **AX-derived URLs stay dropped.** Only an observation whose
   `source.provider` is `companion` may carry `resource.kind === 'url'`; the
   rule in `normalizeObservation` becomes provenance-aware rather than
   unconditional. A browser window seen through Accessibility still contributes
   nothing.
7. **No content, ever.** The extension reads no DOM, no selection, no page text,
   no form values. It listens to tab activation/update events and the window
   focus state, and reports metadata only. `verify:privacy` gains the extension
   to its scan and its symbol denylist gains the content-bearing APIs
   (`document.body`, `getSelection`, `innerText`, `value`) for that directory.

## Consequences

- A new listener means a new failure mode: the port may be taken. The plugin
  reports "companion intake unavailable" in the panel and keeps capture working;
  the extension surfaces a pairing error instead of silently dropping events.
- The token is a bearer credential on the local machine: any process that can
  read `chrome.storage.local` or sniff loopback could use it. Loopback binding,
  rotation and revocation bound that risk; a malicious local process was already
  in the threat model's "attacker in the user's session" row.
- Retiring the roadmap's browser clause requires the privacy matrix below to
  pass on a real Chrome, not a fixture.
